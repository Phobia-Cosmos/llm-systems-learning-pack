# Qwen3 A100 单卡 Serving 压测

测试日期：2026-07-29

环境：NVIDIA A100-SXM4-40GB、PyTorch 2.6.0+cu124、vLLM 0.8.5、SGLang 0.4.6.post5、Qwen3-8B BF16。服务上下文上限为 8192 tokens，单模型测试显存利用率上限为 85%。

所有单模型和双模型请求均成功，没有 OOM、超时或 HTTP 错误。

## 关键结果

| 负载 | 引擎 | 输入吞吐 tokens/s | 输出吞吐 tokens/s | P95 延迟 s | P95 TTFT s |
| --- | --- | ---: | ---: | ---: | ---: |
| 约 332 输入 tokens，并发 32 | vLLM | 7657.0 | 1408.9 | 1.732 | 0.653 |
| 约 332 输入 tokens，并发 32 | SGLang | 7904.5 | 1454.5 | 1.723 | 0.713 |
| 约 2703 输入 tokens，并发 16 | vLLM | 16549.8 | 394.9 | 3.728 | 2.479 |
| 约 2703 输入 tokens，并发 16 | SGLang | 17318.4 | 413.2 | 3.664 | 2.366 |
| 约 7314 输入 tokens，并发 16 | vLLM | 61274.3 | 536.2 | 1.900 | 0.193 |
| 约 7314 输入 tokens，并发 16 | SGLang | 62651.2 | 548.2 | 1.865 | 0.210 |
| 约 8022 输入 tokens，并发 16 | vLLM | 23633.5 | 188.6 | 5.420 | 4.403 |
| 约 8022 输入 tokens，并发 16 | SGLang | 54290.0 | 433.1 | 2.361 | 0.631 |

7.3K 并发 16 比并发 8 更快，是因为 16 个请求在同一批次完成，而并发 8 的 16 个请求分成了两批；不能把这两行直接解释为并发越高单请求越快。近 8K 结果使用相同请求数量，更适合直接比较引擎。

SGLang 的监控文件包含较多服务启动和等待阶段样本，因此整个活跃样本的平均利用率不适合直接与 vLLM 的平均值比较；峰值和逐请求 JSON 更可靠。

## 双模型测试

同一张 A100 上同时运行 Qwen3-8B 与 Qwen3-0.6B 两个 vLLM 实例。8B 实例先以 62% 整卡预算启动；第二个实例必须把 `gpu_memory_utilization` 设为 92%，因为 vLLM 0.8.5 会把已经存在的第一个进程显存也计入第二个实例的整卡总占用上限。两个服务稳定后占用约 37.6 GiB。

| 模型与负载 | 成功/失败 | 输入吞吐 tokens/s | 输出吞吐 tokens/s | P95 延迟 s | P95 TTFT s |
| --- | ---: | ---: | ---: | ---: | ---: |
| 8B，2.7K，上下文并发 8 | 32/0 | 6244.8 | 149.0 | 6.805 | 2.799 |
| 0.6B，2.7K，上下文并发 16 | 64/0 | 21890.7 | 522.5 | 2.584 | 0.782 |
| 8B，7.3K，上下文并发 4 | 8/0 | 6045.9 | 53.0 | 7.794 | 4.624 |
| 0.6B，7.3K，上下文并发 8 | 16/0 | 19575.5 | 171.3 | 4.479 | 1.926 |

双模型共享计算资源时 8B 延迟明显升高。多卡环境应让不同模型使用不同的 `CUDA_VISIBLE_DEVICES`，而不是继续共享一张卡。

各目录中的 JSON 保存每个请求的延迟、TTFT 和 token 数；`gpu.csv` 保存每秒 GPU 利用率、显存、功耗和温度。
